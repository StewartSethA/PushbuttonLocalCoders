# Experimental single-RTX-3090 optimizations

These are explicit experiments, not a replacement for the portable llama.cpp
default. No GPU unlock, kernel installation, bootloader edit or reboot happens
automatically. Runtime preparation does build/download third-party code and
weights: review its source before running it. Docker and NVIDIA Container
Toolkit, a compatible host driver, and sufficient disk/VRAM are prerequisites.
`check` validates supported settings, not memory fit or model quality.

## NInfer: MoE kernels, CUDA Graphs, MTP and compressed KV

The `ninfer-3090` adapter now supports both Qwen3.6-35B-A3B (`qwen3.6:35b`)
and Qwen3.8-27B. It pins the native runtime source to
`115dee6b4d2df1c2d491da498515bdeb4f7e3f01` from
[NInfer-3090](https://github.com/Don-Chad/ninfer-3090).
Its upstream downloader selects a model-specific, pinned, checksum-verified
v3 artifact. Serving selects that exact filename, never the largest cached file.
The current Qwen3.6 artifact is about **21.2 GiB**, not the older approximately
20.84-GiB artifact underlying some published results.

```bash
# Preview without changing the machine:
pushbutton-backend --dry-run serve ninfer-3090 qwen36 \
  --gpus 0 --profile mtp-k8v4 --context 4096

# Builds/downloads/serves, foreground, loopback port 20880:
pushbutton-backend serve ninfer-3090 qwen36 \
  --gpus 0 --profile mtp-k8v4 --context 4096
```

| Profile | KV | Speculation |
| --- | --- | --- |
| `standard` | INT8 | Off; comparison baseline |
| `mtp` (default) | INT8 | MTP, three draft tokens |
| `mtp-k8v4` | Unrotated K8/V4 | MTP, three draft tokens |
| `mtp-rk8v4` | Rotated K8/V4 | MTP, three draft tokens |
| `prompt-lookup` | INT8 | DFlash2 plus 15-token n-gram copies; **Qwen3.8 only** |

CUDA Graphs and prefix reuse remain enabled by the engine. Low-bit profiles
default to 4096 context; use `--context 131072` only as a deliberate capacity
and quality experiment. The adapter never silently reduces requested context.
Allocated context is not evidence of sustained throughput or accurate attention
at that depth. Rotated and unrotated caches must be evaluated separately.

The current pinned engine documents adaptive n-gram lookup alongside DFlash2,
not Qwen3.6 MTP. The adapter rejects that unsupported combination rather than
inventing a flag. Historical claims of 187/262 tok/s and 310-406 tok/s on
copy-rich coding tasks are **project-reported, workload/version-specific**,
not independently verified expectations for this build. Current upstream
documentation reports other model/artifact configurations and different rates.

The server offers OpenAI `/v1/chat/completions` and Anthropic `/v1/messages`
on `http://127.0.0.1:20880`. Use an existing client's custom endpoint support;
for an installed Claude Code client, set `ANTHROPIC_BASE_URL` to that URL
without `/v1`, with a local placeholder auth token. The `claude-local` and
`coder-local` wrappers still provision their existing llama.cpp paths; these
experimental profiles are not automatically substituted into their lifecycle
or capacity/admission guards.

## HyperQwen / patched vLLM dense-model path

`vllm-qwen38-3090` uses the current
[HyperQwen recipe](https://github.com/syv-ai/HyperQwen) container,
`ghcr.io/syv-ai/hyperqwen:latest`. First boot prepares/requantizes its
W4A16-AutoRound model and verifies the installed patches. The mutable image tag
is **not a reproducible source pin**; preserve its local image digest when
recording results. Prefix caching is explicitly enabled.

```bash
pushbutton-backend serve vllm-qwen38-3090 qwen38 \
  --gpus 0 --profile mtp-long --context 150000
```

| Profile | Maximum configured context | Recipe controls |
| --- | --- | --- |
| `dflash2` (default) | 65536 | DFlash2, fast context |
| `standard` | 65536 | No speculation |
| `mtp` | 65536 | MTP, fast context |
| `mtp-long` | 150000 | MTP, long context, specialized attention plugin, INT8 MLP activations |
| `prompt-lookup` | 56000 | DFlash2, 15-token reproduction profile |

The adapter forwards the **exact requested context** as `MAX_LEN`; it no longer
ignores `--context`. Profile limits and unsupported combinations fail before
preparation. The recipe supplies its own fused/GQA-aware attention and graph
implementation; flags from unrelated engines are not interchangeable. INT8
activations and compressed KV can affect quality. Published attention speedups,
including the reported 22% result, are not universal or additive guarantees.

## GPU unlock: separate, manual, recoverable experiment

[gpu-unlock](https://github.com/Zagitta/gpu-unlock) initializes the GPU before
the stock NVIDIA driver. It targets FP16/BF16/TF32 Tensor Core math with **FP32
accumulation**, not all FP16 instructions. Its current documentation reports
3090 BF16 GEMM around 75 to 125 TFLOPS; measurements vary. Quantized decoding
is often bandwidth-bound and may see little or no improvement.

Before installation, have a recovery console, a known-good boot entry,
backups of boot configuration, matching kernel headers, and a plan for Secure
Boot/module signing if applicable. Use a recoverable Linux installation and
review the current upstream distribution-specific instructions. In a reviewed
checkout, upstream's `make install` installs the module/firmware and rebuilds
initramfs; this is a privileged system change, not an inference-server option.
Then manually append `gpu_unlock.targets=all` to the kernel command line while
preserving existing options, regenerate the relevant boot configuration, and
reboot. Never hot-unbind an active display GPU to shortcut that sequence.

Read-only diagnostics:

```bash
pushbutton-backend gpu-unlock-status
journalctl -k -b | grep gpu_unlock
```

Module presence or a boot flag does **not** verify a successful unlock.
Inspect per-card kernel results and measure the same GEMM/prefill workload.
For rollback, remove `gpu_unlock.targets=` in the bootloader's edit screen
for a one-off boot, then remove it from persistent boot configuration and
regenerate the boot entries. Upstream also documents package removal.
If firmware does not stop, upstream advises a full power-off before retrying.
Do not combine the first unlock test with a runtime/kernel change.

## Comparable measurements, not peak-rate marketing

```bash
# Before the manual unlock:
pushbutton-bench qwen36 --backend ninfer-3090 --gpus 0 \
  --profile mtp-k8v4 --context 4096 --suite quick \
  --label controlled --gpu-unlock-state stock

# After the manual unlock, with identical runtime, weights and settings:
pushbutton-bench qwen36 --backend ninfer-3090 --gpus 0 \
  --profile mtp-k8v4 --context 4096 --suite quick \
  --label controlled --gpu-unlock-state unlocked --no-prepare
```

Reports retain resolved profile settings, source revision, context, boot/module
diagnostics, and **operator-reported** unlock state. Profile/state appear in
filenames and the generated index so these A/B reports do not overwrite each
other. The selector does not inherit legacy or different-profile speed samples.
Do not rerun preparation between A/B arms: mutable runtime images would
confound the comparison. Record image digest, power limit, GPU temperatures,
driver, model revision, cache warmth, prompt/output lengths and speculation
acceptance. Benchmark compute-bound GEMM and prefill separately from decoding.

The existing inference suite measures streaming latency and generation rates,
**not coding correctness**. For a coding-agent comparison, use identical clean
repository revisions, tasks, prompts, tool permissions and output budgets.
Record valid tool calls, successful patches, tests passed, first-token latency,
tool time, retry count and total wall-clock time. Evaluate cold and repeated
prefixes separately, and test attention quality at each intended context depth.
Select on successful task completion time, not a copy-heavy peak tok/s number.
